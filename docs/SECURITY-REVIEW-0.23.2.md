## Remaining concerns

1. **Consensus authentication / node trust (high):** wallet RPC blocks contain a kernel and proof leaf, not the proof itself. Local continuity, ownership and accumulator checks do not establish consensus validity or canonical-chain membership. An adversarial server can fabricate an internally consistent view or omit data. Use a trusted validating node. A secure authenticated light-client design needs separate protocol work; two-server comparisons alone are insufficient.
2. **Unknown broadcast availability (medium):** uncertainty is deliberately not cleared by timeout, node rejection or the normal 30-block reservation age. An unconfirmed transaction that can no longer be accepted may leave new payments/recovery blocked until manual investigation. The original data is kept. No automated claim of failure is made. A node acknowledgement/confirmation view is only as trustworthy as the selected node. Reorgs, confirmations occurring before local send registration and conflicting external spends need broader integration tests.
3. **Untrusted response resource use (medium):** responses are parsed without a streaming byte ceiling. A malicious node or very large legitimate response may exhaust browser memory. Appropriate byte limits, adaptive block sizing and adversarial load tests remain to be designed together. Timeouts do not cap bytes.
4. **Encrypted recipient privacy remains experimental:** v3 outer encryption is classical X25519/XSalsa20Poly1305, including with Generation receiving addresses. Recipient anonymity/key privacy needs independent cryptographic review. Compatible apps are required; a malicious sender can expose a normal notification. Address holders can link app addresses sharing a scan public key. Message content itself can identify a person even when encrypted on-chain.
5. **Recovery scope:** all three sub-wallets share one root phrase/password. A backup of that phrase controls all three. Seed replay recovers confirmed receipts and address use, not local labels, unconfirmed outgoing state or unsaved manual off-chain notifications. Imported payment codes may still be required.
6. **Transport privacy limits:** Fast recovery exposes ordinary receiver-ID requests and owned-coin proof lookups to the chosen node. Private scan hides those lookups but still reveals network/range/timing metadata. Tor checks were simulated; no real Tor/IP-leak measurement was performed. Loopback traffic intentionally stays local. Locking clears UI/session storage but an authorized offscreen transaction task can retain its working key until completion.
7. **Release validation:** no fresh release WASM/installed-extension test, live-node relay/mining/real proof acceptance, end-to-end clean restore, full reorg/load testing or external audit has been completed. Encrypted remains disabled on mainnet.

## Independent recovery choices

Use Sub-wallets → select a wallet → Recover assets. Each profile remembers Fast, Private scan or Own node when recovery starts. Defaults are Fast for Standard and Private scan for Auto-refresh/Encrypted. Indexed sub-wallet recovery sends only that profile’s identifiers and coin proof lookups. Known other-profile coins are carried forward only at the exact same height/hash/accumulator; otherwise a local full scan updates their proofs without their owned-coin lookups. The local block scan and network node connection are shared; scans run sequentially. Choosing Own node changes the shared network block source. Initial whole-seed restoration has its own explicitly chosen method for the root wallet. These choices are metadata-query policies, not separate seed/security boundaries.
